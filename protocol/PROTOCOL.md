# ControlDeck Protocol Specification

Version: `protocolVersion = 1`

This document is the single source of truth for the wire protocol used
between ControlDeck peers. It is intentionally platform-independent: the
Android client (Kotlin) and the Windows agent (.NET) each implement their
own DTOs and (de)serializers that conform to this document. Neither
implementation is authoritative over the other — this file is.

## 1. Transport

- Every ControlDeck device runs a WebSocket server on a local TCP port
  (default `47531`) bound to all LAN interfaces.
- Every ControlDeck device can also act as a WebSocket client and connect
  out to peers it has paired with.
- Connections are LAN-only, plain `ws://` for the MVP. The message framing
  and handshake are designed so a future version can switch to `wss://`
  (TLS) without changing the JSON contract — only the socket factory
  changes. A `secure: false` field on `HELLO` reserves this for later.
- Each JSON message is sent as a single WebSocket text frame.
- Encoding: UTF-8 JSON, one object per frame, no batching.

## 2. Envelope

All messages share a common envelope:

```json
{
  "protocolVersion": 1,
  "type": "ACTION",
  "messageId": "b3d6e2b0-...-uuid",
  "sourceDeviceId": "uuid-of-sender",
  "targetDeviceId": "uuid-of-recipient",
  "timestamp": 1723600000000,
  "payload": { }
}
```

- `messageId`: UUID, unique per message. Used for de-duplication and for
  correlating `ACTION` → `ACTION_RESULT`.
- `targetDeviceId` is optional for broadcast-ish messages (e.g. `PING`) but
  required for `ACTION`.
- `timestamp`: sender's epoch milliseconds. Used only for diagnostics/last
  -write-wins comparisons where explicitly specified — never trusted as an
  auth mechanism, since clocks are not synchronized.
- `payload`: type-specific object, see below.

Unknown fields in `payload` MUST be ignored by receivers (forward
compatibility). Unknown `type` values MUST produce an `ERROR` response
with `code = UNSUPPORTED_MESSAGE_TYPE` rather than crashing the
connection.

## 3. Message types

```
HELLO             connection bootstrap, protocol/version exchange
PAIR_REQUEST      initiate pairing (PIN or QR-derived token)
PAIR_RESPONSE     accept/reject pairing, returns shared secret
AUTH              authenticate an already-paired connection
AUTH_RESULT       accept/reject AUTH
DEVICE_INFO       device identity (id, name, platform, version)
CAPABILITIES      list of supported capability strings
ACTION            command to execute on the target device
ACTION_RESULT     outcome of an ACTION
STATE_UPDATE      unsolicited push of current device state (e.g. volume changed locally)
DASHBOARD_SYNC    full dashboard document + version
DASHBOARD_ACK     acknowledges receipt/applied version
ERROR             structured error
PING / PONG       liveness
```

### 3.1 HELLO

Sent immediately after the TCP/WebSocket connection opens, by the
connecting (client) side, then echoed back by the accepting (server)
side.

```json
{
  "type": "HELLO",
  "payload": {
    "protocolVersion": 1,
    "deviceId": "uuid",
    "deviceName": "Gaming PC",
    "platform": "WINDOWS",
    "appVersion": "0.1.0",
    "secure": false
  }
}
```

If `protocolVersion` is incompatible (major mismatch), the receiver
responds with `ERROR { code: PROTOCOL_VERSION_MISMATCH }` and closes the
connection.

### 3.2 Pairing

Pairing establishes a long-lived shared secret between two devices. It
happens once per device pair; afterwards `AUTH` is used to re-authenticate
new connections.

**QR flow**: the target device displays a QR code encoding
`{ deviceId, pairingToken, port }`. The initiating device scans it and
sends `PAIR_REQUEST` with that `pairingToken` over a fresh connection to
the advertised `deviceId`.

**PIN flow**: the target device displays a random 6-digit PIN
(`pairingToken` is the PIN as text) generated for a short-lived pairing
window (2 minutes). The initiator enters it manually.

Both flows use the same message shape — the PIN is simply a
low-entropy, human-typeable `pairingToken`.

```json
// PAIR_REQUEST
{
  "type": "PAIR_REQUEST",
  "payload": {
    "requesterDeviceId": "uuid",
    "requesterDeviceName": "Living Room Tablet",
    "requesterPlatform": "ANDROID",
    "pairingToken": "481927"
  }
}
```

```json
// PAIR_RESPONSE
{
  "type": "PAIR_RESPONSE",
  "payload": {
    "accepted": true,
    "reason": null,
    "deviceId": "uuid-of-responder",
    "deviceName": "Gaming PC",
    "platform": "WINDOWS",
    "sharedSecret": "base64-32-random-bytes"
  }
}
```

On rejection: `accepted: false`, `reason: "TOKEN_INVALID" | "TOKEN_EXPIRED" | "DECLINED"`,
`sharedSecret: null`.

The `sharedSecret` is generated by the responder using a CSPRNG (256-bit),
persisted by both sides associated with the peer's `deviceId`, and never
transmitted again in plaintext after this exchange. It is never logged.

### 3.3 AUTH

Used on every subsequent connection between two already-paired devices,
right after `HELLO`.

```json
{
  "type": "AUTH",
  "payload": {
    "deviceId": "uuid-of-sender",
    "proof": "HMAC-SHA256(sharedSecret, messageId + timestamp)"
  }
}
```

```json
{
  "type": "AUTH_RESULT",
  "payload": { "accepted": true, "reason": null }
}
```

The `proof` binds the shared secret to this specific message
(`messageId`/`timestamp`) so it is not a static bearer token replayable
verbatim across connections. This is a lightweight MVP scheme, not a
substitute for TLS; `wss://` remains the intended upgrade path for
stronger guarantees.

### 3.4 DEVICE_INFO / CAPABILITIES

Exchanged right after successful `AUTH` (or right after pairing
completes), and whenever local capabilities change.

```json
{
  "type": "DEVICE_INFO",
  "payload": { "deviceId": "uuid", "deviceName": "Gaming PC", "platform": "WINDOWS", "appVersion": "0.1.0" }
}
```

```json
{
  "type": "CAPABILITIES",
  "payload": {
    "deviceId": "uuid",
    "capabilities": ["VOLUME", "MUTE", "MEDIA_PLAY_PAUSE", "MEDIA_NEXT", "MEDIA_PREVIOUS", "APP_LAUNCH"],
    "apps": [
      { "appId": "spotify", "displayName": "Spotify" },
      { "appId": "discord", "displayName": "Discord" }
    ]
  }
}
```

Capability enum (`BRIGHTNESS`, `VOLUME`, `MUTE`, `MEDIA_PLAY_PAUSE`,
`MEDIA_NEXT`, `MEDIA_PREVIOUS`, `APP_LAUNCH`) is closed for the MVP but
receivers must tolerate unknown future values (ignore them, don't crash).
`apps` is an open, locally-resolved catalog (see §8).

### 3.5 ACTION / ACTION_RESULT

```json
{
  "type": "ACTION",
  "sourceDeviceId": "tablet-id",
  "targetDeviceId": "pc-id",
  "payload": {
    "action": { "type": "BRIGHTNESS_SET", "value": 70 }
  }
}
```

Action types:

| type | payload fields | semantics |
|---|---|---|
| `BRIGHTNESS_SET` | `value: Int (0-100)` | absolute |
| `VOLUME_SET` | `value: Int (0-100)` | absolute |
| `SET_MUTED` | `muted: Boolean` | absolute |
| `MEDIA_SET_STATE` | `state: "PLAYING" \| "PAUSED"` | absolute, resolved via PLAY/PAUSE locally |
| `MEDIA_NEXT` | — | edge-triggered |
| `MEDIA_PREVIOUS` | — | edge-triggered |
| `APP_LAUNCH` | `appId: String` | resolved to a local app locally |

```json
{
  "type": "ACTION_RESULT",
  "payload": {
    "correlatesTo": "messageId-of-the-ACTION",
    "success": true,
    "errorCode": null,
    "resultingState": { "type": "BRIGHTNESS_SET", "value": 70 }
  }
}
```

`errorCode` (when `success: false`): `UNSUPPORTED_CAPABILITY`,
`APP_NOT_FOUND`, `PLATFORM_ERROR`, `INVALID_VALUE`.

### 3.6 STATE_UPDATE

Push notification when a device's own state changes locally (e.g. user
changed system volume outside ControlDeck). Same shape as
`resultingState` above, unsolicited (no `correlatesTo`). Used to keep the
observer's dashboard fresh and to seed group/reconnect logic.

### 3.7 DASHBOARD_SYNC / DASHBOARD_ACK

```json
{
  "type": "DASHBOARD_SYNC",
  "payload": {
    "dashboard": { "id": "uuid", "name": "Gaming", "version": 14, "widgets": [...], "groups": [...] }
  }
}
```

```json
{
  "type": "DASHBOARD_ACK",
  "payload": { "dashboardId": "uuid", "appliedVersion": 14 }
}
```

Conflict resolution is last-write-wins by `version` (monotonically
increasing integer, incremented by whichever device edits). See
`docs/ARCHITECTURE.md` §Dashboard sync for the exact tie-break rule.

### 3.8 ERROR / PING / PONG

```json
{ "type": "ERROR", "payload": { "code": "UNSUPPORTED_MESSAGE_TYPE", "message": "...", "correlatesTo": "messageId-or-null" } }
```

Error codes: `PROTOCOL_VERSION_MISMATCH`, `UNSUPPORTED_MESSAGE_TYPE`,
`MALFORMED_PAYLOAD`, `NOT_PAIRED`, `AUTH_FAILED`, `UNSUPPORTED_CAPABILITY`,
`INVALID_ACTION`, `INTERNAL_ERROR`.

`PING`/`PONG` carry no payload beyond the envelope and are sent every 15s
by each side; 3 missed `PONG`s (45s) mark the peer offline and close the
socket.

## 4. Connection lifecycle

```
connect (TCP)
  -> HELLO (initiator) -> HELLO (acceptor)
  -> [not yet paired?]  -> PAIR_REQUEST/PAIR_RESPONSE
  -> AUTH -> AUTH_RESULT
  -> DEVICE_INFO, CAPABILITIES (both directions)
  -> steady state: ACTION/ACTION_RESULT, STATE_UPDATE, DASHBOARD_SYNC/ACK, PING/PONG
  -> disconnect (network loss, app close) -> peer marked OFFLINE, reconnect policy engages on next connect
```

Reconnection is initiated by whichever side has an outstanding pairing
and periodically retries discovery + connect while the peer is offline
(see `docs/ARCHITECTURE.md` §Reconnect policy).

## 5. Discovery (out of band, not WebSocket)

mDNS/DNS-SD service type: `_controlldeck._tcp.local.`

TXT records:
```
id=<deviceId>
name=<deviceName>   (may be percent-decoded on read)
platform=ANDROID|WINDOWS
version=<appVersion>
port=<websocket-port>
```

The advertised `deviceId` is what the UI keys off of — never the resolved
IP/hostname, which may change at any time.

## 6. Versioning / forward compatibility

- `protocolVersion` is a single integer, bumped on breaking envelope or
  message-shape changes only. Additive fields do not bump it.
- Receivers MUST ignore unknown JSON fields and unknown enum values
  (falling back to a safe default, e.g. treating an unknown capability as
  absent, an unknown action as `UNSUPPORTED_CAPABILITY`).
- A receiver on a newer `protocolVersion` than the sender should still
  process older messages when the shapes are compatible; a major
  incompatibility yields `PROTOCOL_VERSION_MISMATCH`.

## 7. Security notes (MVP scope)

- No accounts, no cloud, no external identity provider.
- Trust is established once via QR/PIN pairing and then carried by the
  persisted `sharedSecret` + per-message HMAC proof.
- Because this is LAN-only `ws://`, the HMAC proof stops a passive
  eavesdropper from replaying old traffic to authenticate blind, but it
  does **not** provide confidentiality on the wire. `wss://` (TLS) is the
  documented upgrade path once certificate provisioning for LAN peers is
  designed; nothing in this message contract needs to change to add it.
- Pairing secrets and PINs are never written to logs.

## 8. Application launch resolution

The protocol only ever carries an opaque `appId` (e.g. `"spotify"`). Each
device maintains its own local app registry mapping `appId` →
platform-specific launch mechanism:

- **Android**: `appId` → package name (`com.spotify.music`), launched via
  `PackageManager.getLaunchIntentForPackage`.
- **Windows**: `appId` → an entry in a user-editable app registry
  (executable path, or a shell `AppUserModelID`/protocol handler),
  launched via `Process.Start`.

The dashboard/widget model only ever stores the `appId`; it is resolved
locally by the target device at execution time. No filesystem paths ever
cross the wire.
